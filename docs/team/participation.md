# Особиста участь у спринтах 3–5

Кожен учасник С4 додає три власні методи JUnit і комітить їх зі свого облікового запису. Один змістовний коміт може містити всі три методи та бути першим комітом учасника. Кожен метод перевіряє окрему поведінку. Параметри одного методу зараховуються як один тест. Автор пояснює очікувані результати на демо.

## Стан поданих внесків

Чотири заповнені класи отримано й перевірено на обох модулях. [Результати й контрольні суми](individual-junit.md) · [Персональний коміт у браузері](github-contributions.md)

## Початкові завдання JUnit

Файли створюються в `src/test/java/ua/kpi/tzyapz/personal/`. Імена класів різні, тому над ними можна працювати паралельно. У кожному методі потрібні `@Test`, `@DisplayName` з ID правила, підготовка даних, виклик та конкретне твердження. Джерело — SRS П3 §5 з правкою BL-50. [Матриця BL](../coverage-matrix.md)

1. Завантажте свій Java-шаблон і відкрийте його у звичайному текстовому редакторі. Замініть три виклики `fail` власними викликами методів і твердженнями. Збережіть те саме ім’я файлу в UTF-8. Для `BigDecimal` використайте десятковий рядок та потрібну шкалу.
2. Надішліть Марку свій файл у Telegram і додайте одне речення, чому один результат очікуваний. Марко зможе перевірити компіляцію й запустити класи одним прогоном.
3. Після погодження публікації увійдіть у GitHub під своїм обліковим записом. Відкрийте папку `src/test/java/ua/kpi/tzyapz/personal/` у гілці досьє, натисніть **Add file → Upload files**, виберіть свій файл і запропонуйте коміт у новій гілці. У PR перевірте, що ціль — гілка досьє, а автор коміту — ваш обліковий запис. Передайте Марку посилання. Злиття через **Create a merge commit** збереже початковий коміт. [Завантаження файлу](https://docs.github.com/en/repositories/working-with-files/managing-files/adding-a-file-to-a-repository) · [Способи злиття PR](https://docs.github.com/en/pull-requests/reference/pull-request-merges)

**Перевірка робочого середовища.** Методичка `04_Спринт4_Автоматизація.pdf`, с. 15: «перевірити на кожному робочому місці mvn -v (JDK 17) і mvn test (7 тестів проходять)». Кожен у власному середовищі один раз відкриває папку `code/starter/` з оригінального ZIP С4, запускає `mvn -v` та `mvn test` і передає в одному повідомленні вивід із Java 17 і `Tests run: 7, Failures: 0, Errors: 0, Skipped: 0`. Варіант спільного підготовленого середовища або хмарної машини потрібно погодити з викладачем, якщо вони замінюють перевірку робочого місця.

Після внесків Codex може об’єднати коміти зі збереженням історії, запустити той самий розширений набір на оригіналах v1 і v2 та оновити матрицю, журнал і звіт. Поточна статистика стосується наявного набору.

## Взаємна рецензія

**С4, код.** Марко як рецензент С4 охоплює базові тест-класи та внески колег. Його власний клас перевіряє інший студент, наприклад Антон. Для §5.3 перевірте ID і джерело очікуваного результату, AAA й назву, межі, `assertThrows` і шкалу `BigDecimal`, незалежність, явні UI-очікування та зв’язок падінь із MOD-ID. Зауваження залиште у PR або Issue, а позначку рецензента — у матриці чи схваленому PR.

**С3, кейси й дефекти.** Антон як рецензент С3 застосовує §5.3 до кожного актуального ID. Для кейса перевіряє поля, ID вимоги, назву, передумови, атомарні кроки, очікуваний результат, незалежність, тип і пріоритет. Для звіту звіряє заголовок, відтворення, очікування, самостійність дефекту, докази, мову і зв’язок з TC та вимогою. Автор кейса або звіту передає власний внесок на перевірку колезі. Після виправлення колега позначає повторну перевірку.

**С5, досьє.** Роман як рецензент С5 перевіряє дев’ять рядків [чекліста](../sprint5/review-checklist.md). Для звіряння підсумків потрібні звіт, підсумок журналу регресії, матриця, розподіл задач і два протоколи Surefire. Зауваження з підставою фіксуються до виправлення.

Стан отриманих відповідей наведено в [журналі](review-confirmations.md). Формат відповіді `Документ / ID або клас · ПІБ · дата · OK або зауваження · посилання на коміт/PR`. Позначки OK можна надіслати одним повідомленням з повним переліком перевірених ID. Анонімну peer-review форму кожен учасник передає викладачу окремо.

## Підготовка ретро й захисту

Для кожного фактичного спринту кожен учасник може заздалегідь запропонувати Start / Stop / Continue одним повідомленням. Скрам-майстер збирає пропозиції та фіксує погоджені рішення, учасників і справжню дату. Повна заміна спільної 15-хвилинної ретроспективи перепискою потребує погодження викладача. Модератори за статутом — Антон у С3, Марко у С4 і Роман у С5. С5 підбиває підсумки всього семестру.

До захисту кожен готує свій слайд і коротке пояснення правила, доказу та висновку. На живому демо С4 Антон запускає Maven у чистій копії та показує результати. [Розподіл виступу](../sprint5/tasks.md) · [UI-сценарії](../ui-scenarios.md) · [Протокол Maven](../surefire-summary.md)
